# AxeOS Miner Secure Reverse Proxy (NGINX)

Secure HTTPS reverse proxy configuration for **AxeOS-based Bitcoin miners** using NGINX on a Raspberry Pi or Linux server.

This setup allows:

- Secure remote HTTPS access to an AxeOS miner WebUI
- Read-only REST API exposure over WAN
- Blocking dangerous HTTP methods from the Internet
- Allowing only a specific restart endpoint
- TLS encryption with Let's Encrypt
- Protection against unauthorized remote configuration changes

This project was originally created and tested with Bitaxe miners, but the reverse-proxy approach is intended for **AxeOS-compatible miners exposing the same HTTP API/WebUI behavior**.

Other AxeOS-based miners using compatible WebUI and REST API endpoints can use the same reverse-proxy principle.

# Performance

Even a Raspberry Pi Zero 2 W is largely sufficient for handling
multiple AxeOS miner HTTPS reverse proxies simultaneously, as the traffic
volume generated by monitoring APIs and WebUI access is very low.

CPU and RAM usage remain extremely low in normal operation.

# Architecture

```text
Internet
    │
    ▼
Router Port Forwarding
    │
    ▼
Raspberry Pi / Linux Reverse Proxy
    │
    ├── HTTPS :18443 → AxeOS Miner #1
    ├── HTTPS :19443 → AxeOS Miner #2
    └── HTTPS :20443 → AxeOS Miner #3
```

Example public URLs:

```text
https://your-domain.example.com:18443
https://your-domain.example.com:19443
```

# Why This Configuration Is Important

AxeOS miners are commonly accessed through an HTTP WebUI and REST API on the local network. Depending on the device and AxeOS version, these interfaces may not provide the same protections expected from an Internet-facing service, such as:

- HTTPS by default
- Strong Internet-facing authentication/session controls
- CSRF protection
- Advanced access control

If such an interface is directly exposed to the Internet, an attacker knowing the API endpoints could potentially attempt to:

- Change pool configuration
- Change wallet address
- Overclock the miner
- Upload firmware
- Modify system settings
- Reboot the device

This reverse proxy mitigates these risks by:

- Allowing only GET and HEAD for normal access
- Allowing only one specific POST endpoint:
  - `/api/system/restart`

Everything else is blocked by the reverse proxy.

The AxeOS WebUI remains available in read-only mode for normal monitoring use.

> Exact API endpoints can vary between AxeOS versions and miner models. Verify the endpoints used by your miner before exposing it remotely.

# NGINX Configuration

Example file used by the original installation:

```text
/etc/nginx/sites-available/bitaxe
```

The filename itself is arbitrary and does **not** restrict the configuration to Bitaxe hardware. Existing installations can keep this filename unchanged. For a new installation, you may choose another name such as `axeos-miner` as long as the corresponding `sites-enabled` symlink uses the same name.

# Complete Configuration Example

⚠️ IMPORTANT:

The configuration below is intentionally written for **ONE single AxeOS miner only**.

If you want to expose multiple AxeOS miners:

- Duplicate the entire `server {}` block
- Change the listening port
- Change the internal miner IP address

Example:

| Miner | Public Port | Internal IP |
|---|---|---|
| AxeOS Miner #1 | 18443 | 192.168.10.41 |
| AxeOS Miner #2 | 19443 | 192.168.10.42 |
| AxeOS Miner #3 | 20443 | 192.168.10.43 |

Each miner should have:

- Its own `server {}` block
- Its own listening port
- Its own internal IP

---

Replace:

- `your-domain.example.com`
- `192.168.10.41`

with your own values.

```nginx
server {

    listen 18443 ssl;
    listen [::]:18443 ssl;

    server_name your-domain.example.com;

    ssl_certificate /etc/letsencrypt/live/your-domain.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.example.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    #
    # Allow ONLY restart POST endpoint
    #
    location ~ ^/api/system/restart/?$ {

        limit_except POST {
            deny all;
        }

        proxy_pass http://192.168.10.41;

        proxy_http_version 1.1;

        proxy_set_header Host 192.168.10.41;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_read_timeout 90;
    }

    #
    # Everything else = READ ONLY
    #
    location / {

        limit_except GET HEAD {
            deny all;
        }

        proxy_pass http://192.168.10.41/;

        proxy_http_version 1.1;

        proxy_set_header Host 192.168.10.41;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_read_timeout 90;
    }
}
```

# Enable Site

For the original `bitaxe` filename shown above:


If you choose a different filename, use that same filename in both `sites-available` and `sites-enabled`.

# Security Notes

## This setup protects against:

- Unauthorized configuration changes through blocked HTTP methods
- Remote overclocking through blocked write endpoints
- Unauthorized firmware updates through blocked write endpoints
- Wallet hijacking through blocked configuration endpoints
- Pool hijacking through blocked configuration endpoints
- Generic REST API write abuse

---

## This setup DOES NOT protect against:

- Vulnerabilities inside AxeOS itself
- Vulnerabilities in the miner WebUI or allowed GET endpoints
- Compromised LAN devices
- Exposed SSH services
- Physical access attacks
- Misconfigured router/firewall rules

---

# Recommended Additional Security

- Strong router admin password
- Disable UPnP
- Keep Raspberry Pi/Linux server updated
- Keep AxeOS firmware updated
- Use non-standard public ports
- Restrict access by IP if possible
- Never expose the miner's raw HTTP interface directly to the Internet
